## Part 2 — Live permission audit (throwaway accounts A/B)

Method: mirror the app's exact auth flow over REST (phone → internal email `p.<slug>@members.example.com`,
signUp with `consent` + name/phone, then function-calls). One throwaway user was created, exercised, and
**deleted**; deletion verified (login now fails). No real data touched; no keys or tokens stored in this
report.

Result: **37 checks pass / 0 fail / 6 skipped.**

### Anon (not signed in) — all passed
- `SELECT` on `members`, `offers`, `visits`, `businesses`: all `401 permission denied`.
- `UPDATE businesses`: denied.
- Every RPC denied to anon except the two intended publics: `get_business` and `daily_public` are 200.
  All others (`daily_status`, `play_daily`, `join_business`, `import_members`, `my_card`, `add_stamp`,
  `claim_reward`, `redeem_code`, `delete_member`, `reset_member_password`, `set_wa_optout`,
  `set_my_wa_optout`, `delete_me`, `_code`, `_give`) → `401 permission denied`.

### Authenticated customer, no member row — all passed
- Selects `members`/`offers`/`visits`: empty (RLS scopes nothing).
- `SELECT id FROM businesses`: empty (RLS hides even ids from non-owners; the owner row can't be targeted).
- `PATCH businesses` (id-filtered, `Prefer: count=exact`): **0 rows affected** for both a granted column
  (`daily_notes`) and a protected one (`name`) — column grants exist but `biz_owner_update` RLS blocks
  non-owners. `join_token`/`scan_token` are updatable columns but only within RLS owner-scoped rows.
- `get_business` response does not include `join_token`/`scan_token` (verified against returned columns).
- `redeem_code`, `reset_member_password`, `delete_member` vs an arbitrary uuid: all `400 Not allowed`.
- `join_business` with `consent=false`: rejected (`Consent is required to join`).
- `join_business` without a join token: rejected (`Please scan the sign-up QR code at the counter to join`).
- `add_stamp` with a wrong token: `invalid`; nothing awarded.

### Additional (static) verification where live was blocked
- **Daily scratch once-per-day is race-free**: `play_daily` locks the member row
  (`select … for update`) before the "already played today" check, so 20 parallel calls serialize →
  exactly one win; the rest return `done`.
- **XSS via member name / business text is inert**: every HTML insertion path wraps untrusted values in
  `esc()` (escapes `& < > " '`); numeric interpolations are the only unescaped ones. Join-name, offer
  text/code, reward text, customer list, redeem log, search inputs — all escaped.

## Findings / notes
- Supabase email confirmation is **off** (signUp returns a session immediately) — by design for phone
  sign-in; self-registration is harmless because anon has nothing and non-owner writes are RLS-blocked.
- Member column name is `last_daily` (not `daily_date` as the Part-1 brief said); `daily_streak` is
  `int default 0`. `play_daily`/`daily_status` read `last_daily`. schema.sql matches the live v2 SQL.
- Weekly cap is a rolling 7-day window (not a Mon–Sun week) computed in the business timezone.
- Security headers + CSP already verified on the deployed alias; note the enforced CSP now applies to
  the manifest (`manifest-src 'self' blob:`).
